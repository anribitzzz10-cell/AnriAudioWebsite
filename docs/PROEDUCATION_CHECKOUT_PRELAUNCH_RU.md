## Что подтверждено и что не подтверждено
- Пользователь сообщил о доступе в кабинет и разнообразных доступных странах/способах в интерфейсе DEMO. Конкретная работоспособность каждого способа для этого магазина ещё не подтверждена платежами.
- Публичная документация Prodamus описывает GET/POST checkout, подпись запроса, webhooks и возвратные URL. ЭТО НЕ ДОКАЗЫВАЕТ, что все параметры и методы идентично реализованы у конкретного KZ-мерчанта Proeducation.
- Кабинет https://anriprod.proeducation.kz/ невозможно проинспектировать из текущего доступа к публичным страницам; точные merchant settings, доступные валюты, webhook ключ и SYS должны быть проверены в авторизованном Work-сеансе. Никаких паролей, ключей, реквизитов покупателя не публиковать.
- Сайт сейчас содержит отключённый checkout, существующая функциональность плагина и лицензий не менялась. Эту ветку НЕ сливать в main автоматически.

## UI на сайте: что готовим
1. EN/RU/KK: «ANRI AUDIO MIDI — $39, one-time perpetual license» / «39 USD, разовая бессрочная лицензия»; заметка: реальная валюта и итоговая сумма на платёжной странице до подтверждения заказа.
2. Отдельно указывать Proeducation как запланированную платёжную страницу; до запуска оставить Buy отключённой. Не показывать фиктивные логотипы или гарантированные «все страны/банки принимаются».
3. Перед оплатой покупатель должен видеть описание ПО, поддерживаемую платформу, цену и валюту списания, условия лицензии, возврата, контакты, политику конфиденциальности.
4. Показать статус «Ожидаем подтверждения оплаты», «Оплачено — создаём лицензию», «Лицензия готова», «Оплата не подтверждена», «Нужна поддержка».
5. Не принимать карточные данные непосредственно на anriaudio.com. Не привязывать кнопку к главной ссылке формы с произвольно редактируемой суммой — требуется подписанный заказ.

## Backend: предлагаемая схема (не реализована)
Browser (anriaudio.com) -> POST /v1/checkout/proeducation/create (Anri Cloud; server-side, rate limit)
  -> создать Order: UUID, sku ANRI_AUDIO_MIDI_MAC_AUV2, quantity=1, expected_amount, currency, email, status=pending
  -> сервер формирует ПОДПИСАННЫЙ запрос заказа к конкретной форме merchant (секрет только в backend)
  -> отдать клиенту проверенный checkout URL/redirect.
Покупатель -> Proeducation -> POST /v1/payments/proeducation/webhook -> Anri Cloud:
  - принимать application/x-www-form-urlencoded / multipart/form-data согласно финально проверенной форме; лимиты размеров/вложенности;
  - проверять Sign из заголовка HMAC SHA-256 по канонизации полей, указанной в документации Prodamus, constant-time comparison;
  - проверить домен формы, merchant/sys и order_num, найти заранее созданный pending order;
  - сверить sku, количество, сумму, валюту с серверной записью заказа; не принимать доверенные с клиента product/amount;
  - только подтверждённый payment_status=success => атомарный переход Order paid (один раз) -> выдача лицензии ANRI Cloud с idempotency key merchant+transaction;
  - повторные, запоздалые и параллельные webhooks должны возвращать результат без второй лицензии;
  - demo callbacks никогда не создавать FULL-лицензию; отличающиеся demo подписи не считать боевыми;
  - cancelled/denied/refund/chargeback учитывать отдельно без автоматической повторной выдачи ключа;
  - при неполном результате сохранить заказ для повторной обработки и аудита, не терять подтверждённые оплаты.
  - вернуть HTTP 200 только после надёжного принятия/сохранения события; иначе провайдер повторит webhook.
  - критические данные и секреты не печатать в логи.
Fulfillment:
  - использовать существующую модель лицензий ANRI Cloud (Ed25519, активация до двух устройств по утверждённой политике);
  - сохранять ключ зашифрованно, отдать покупателю через защищённый механизм после verified payment и отправить e-mail без раскрытия в URL;
  - процесс отправки устойчив к повторам, email delivery failure не создаёт новые лицензии.
URL возврата /checkout/result?order=... — показывает статус backend-записи; НИКОГДА не маркирует заказ paid сам по себе.

## Предварительные параметры checkout
- do=pay (или do=link при выдаче персональной ссылки); products[0][name], products[0][price], products[0][quantity] = 1.
- order_id = внутренний order number; ожидаемый ответ order_num = внутренний номер, order_id = ID провайдера.
- customer_email; customer_phone запрашивает платёжная форма при отсутствии параметра.
- currency: usd / kzt / rub / eur по документации; фактический выбор для KZ-партнёра — только после проверки кабинета.
- urlSuccess (возврат на сайт, не доказательство оплаты), urlReturn (отказ/возврат), URL webhook в настройках.
- sys / urlNotification: проверить доступность и согласование с провайдером, поскольку документация содержит неоднозначные примеры.
- НЕ использовать subscription, recurring, autodebit или demo_mode=1 в production.

## Требования к тестированию (один цикл после реализации)
- Подписанный заказ, корректная цена/валюта, редирект, ввод e-mail.
- webhook: valid success -> ровно одна FULL лицензия; duplicate -> 0 дополнительных; invalid signature, unknown order, wrong amount, wrong currency -> 0 лицензий.
- return success URL до webhook -> order всё ещё pending.
- demo payment/callback -> 0 live лицензий; cancellation/denial/refund -> отсутствие новой выдачи.
- email/link recovery, DB outage/retry, журнал событий, безопасность секретов.
- Сначала Railway staging + подставные данные; затем одна согласованная реальная тестовая оплата после включения live.
- Продакшен, main, A2M1/Broker/SEND MIDI и текущие установщики не менять до отдельного решения.

## Чего не хватает для боевого запуска
1. Заявление подписано и Proeducation подтвердил живой режим (из письма: до этого DEMO).
2. Проверить в личном кабинете доступные currency/methods для мерчанта, режим интеграции, secret/signature и возможность server-side link/create.
3. Выбрать точную цену списания: USD 39 если USD доступен для данного метода, либо утверждённую фиксированную KZT сумму; никаких произвольных курсов в клиентском JS.
4. Проверить документированные notification/event payload, статус возвратов, процедуру возврата и отражение комиссий в отчёте.
5. Подготовить и утвердить страницы Terms of Sale, license agreement, refund/privacy, download и поддержку, а также финально подписанный/notarized установщик.
6. В Railway staging подготовить checkout + webhook + выдачу лицензии; secret хранить только в secrets менеджере. Никаких реальных ключей в репозитории или клиентском JavaScript.
